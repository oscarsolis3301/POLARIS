## Purpose
Every repo POLARIS runs in gets fewer lookups without anyone pasting "reorganize this" again.
`polaris hops` (inside `kit/ops/index.py`, so it ships everywhere) measures how many folders one change
touches and proposes moves; the tidy lane (`ops/roles/TIDY.md`) makes only the moves `hops --proof`
shows changed nothing but paths, writes folder guides, and lands as ONE task; `pack` carries the guides
to builders; `where` writes a ≤ 15-line root map into CLAUDE.md; `next` / `triage` / `update` say when
the pass is due. Failure is safe: a move that cannot be proven is skipped and recorded, never shipped.

## § 0 Shared formats — code against these byte for byte
### 0.1 Guide block — a folder's `<dir>/CLAUDE.md`
- A guide is a TRACKED `<dir>/CLAUDE.md` (dir ≠ the repo root) holding a line that is exactly
  `<!-- polaris:guide -->`. The block runs to the next line that is exactly `<!-- /polaris:guide -->`
  (none → to EOF). Text outside the markers is the human's: never read, never rewritten.
- Purpose line = the first non-blank line inside the block with leading `#` characters and spaces
  removed. Body ≤ 25 lines (markers not counted); a reader prints at most the first 25.
- A citation = a backtick span inside the block with no whitespace, no `://`, no `*`, not starting with
  `-`, `$` or `<`, that contains `/` or ends in `.` + 1–8 letters/digits. It resolves against the
  guide's folder, then the repo root (a trailing `/` = a directory). Neither exists → STALE.
- Plain Markdown, no POLARIS commands — a guide must still help after an uninstall, for any agent or
  person. A folder whose CLAUDE.md exists without the marker gets the block APPENDED (one blank line,
  then the block), never a rewrite. Guides hold stable knowledge only; file lists and symbols stay in
  the generated code map, so adding a file never requires a guide edit.

### 0.2 Root map block — the repo-root `CLAUDE.md`
- Between a line `<!-- polaris:where -->` and a line `<!-- /polaris:where -->`. First write: directly
  below the line `<!-- POLARIS:END -->` (no END marker → appended at EOF); later writes replace the
  block where it sits. Body ≤ 15 lines:
  - line 1 `## Where things live`
  - line 2 ``_Generated by `ops/polaris where` from ops/MAP.md and the folder guides — edit those, not this._``
  - ≤ 13 item lines `` - `<path>` — <purpose> `` (+ ` · guide` when that folder has a guide); more than
    13 → the 13th becomes `- … <N> more in ops/MAP.md`.
- Items, first occurrence of a path wins: `ops/MAP.md` `## Entry points` rows → `## Modules` rows →
  `## Deltas` lines whose text starts with a path then ` — ` → every guided folder not yet listed
  (purpose = its guide's purpose line). A row is a table line `| <c1> | <c2> | …` (header and `|---`
  lines skipped; path = c1 minus backticks and spaces; purpose = c2) or a list line
  `<path> — <purpose>` / `- <path> — <purpose>` (a Delta's trailing `  (<ID>, <date>)` dropped).
  Purposes are cut at 90 characters with `…`; an empty purpose on a guided folder takes the guide's.
- A projection, never a second source: the facts live in MAP.md and the guides.

### 0.3 Moves file — `.polaris/hops-plan.tsv` and every `<moves.tsv>` argument
- TSV, LF; blank and `#` lines ignored. Rows: `move<TAB><from><TAB><to>` (renamed; content changes only
  in imports and path mentions) · `merge<TAB><from><TAB><into>` (from's content folds into `into` and
  `from` disappears — only with the human's up-front yes).
- Repo-relative files, `/` separators, never directories. A Unity `.meta` is never listed: it travels
  with its asset (`--owned` adds it, TIDY's `git mv` carries it).
- A relative `<moves.tsv>` resolves against the current directory, then against the primary
  (`POLARIS_ROOT`) — so `.polaris/hops-plan.tsv` works from a tidy task's worktree.

### 0.4 `ops/LAYOUT.tsv` — the layout record (owner state, like RULES.tsv)
- Line 1 exactly `# path<TAB>verdict<TAB>why — the layout record; polaris hops never proposes a keep row`.
  Rows `<path><TAB><keep|moved|merged|split><TAB><why>`; `<path>` = a file or a `dir/` prefix.
- `keep` = never proposed again (`framework convention` · `proof failed: <reason>` ·
  `broke <check>: <first line>` · `unsure — left for you`). `moved`/`merged`: path = the OLD path,
  why = `→ <new path> · hops-<version>`.
- Written only by TIDY inside its own task. `install.sh` and `update` never write it; update's dirt
  test treats it as state (§ 5). In-flight paths get no row — they are retried next pass.
- The last pass = the newest `<base>` commit that touched `ops/LAYOUT.tsv` (the cooldown's anchor).

### 0.5 `.polaris/hops-due` — the verdict cache
- One LF line `<base-sha><TAB><0|1><TAB><message>`: `0` due, `1` not due; message = the `--due` line, or
  `-`. Written ONLY by `hops --due` (index.py), on every run, both verdicts.
- Refreshed by `done`, `seal` (integrate.sh) and `heal` (admin.sh — every update and every live-board
  install runs it) with exactly `"$SELF" hops --due >/dev/null 2>&1 || true`, after the caller's own
  work succeeded. Never a caller failure; until T-241/T-251 land the call is a silent no-op.
- Readers (`next`, `triage`, the update hint) READ the file and never run hops (`next` lives on the
  anchor hook's 10 s clock). Due ⇔ the file exists AND field 2 is `0` AND field 1 equals
  `git -C "$PRIMARY" rev-parse --verify -q "$BASE"` AND `cfg hops on` is not `off`. Anything else = not
  due, silently. Readers strip a trailing `\r` from every field. Readers inline the check (no new fn).

### 0.6 The once-per-session marker — `.polaris/handover/<sid>/tidy`

### 1.1 The resolver (T-234) — also makes `find --importers` sound for the Planner
- `resolve_import(raw, src, paths, bybase, aliases=None, pyroots=None)`: the new keyword params default
  to None, so every existing caller and selfcheck case is unchanged; `build()` passes both.
- aliases — from every tracked `tsconfig.json` / `jsconfig.json`: `compilerOptions.paths`
  (`"@/*": ["src/*"]` → prefix `@/`, targets relative to `baseUrl`, itself relative to the config's
  folder) and a bare `baseUrl` (a spec `x/y` tries `<cfgdir>/<baseUrl>/x/y`). A config applies to the
  files under its folder; the nearest wins. Parsed leniently (`//` and `/* */` comments and trailing
  commas stripped); `extends` is NOT followed (one comment line says so). Tried before the existing
  fallbacks, each candidate with the relative-import extension list (+ `/index.<ext>`).
- pyroots — `["src"]` when any tracked `src/<pkg>/__init__.py` or `src/<mod>.py` exists, else `[]`.

  followed by a character that is not a letter, digit or `_` (or the line's end) — so
  `components/CartItem` never matches `components/Cart`.

  `<file>:<line><TAB>mention <tail>` (same sort and `-n` cap). No mention → byte-identical to today.
- selfcheck gains ≥ 4 resolve cases (paths alias · bare baseUrl · python src root · python package
  `__init__.py`) and ≥ 2 mention cases (a tail found in a JSON or Dockerfile line; `components/CartItem`

### 1.5 Findings, the screen, `--tsv`, `--stale` (T-241)
- Clusters: weight w(a,b) = commits touching both + 2 when either imports the other; movable files
  only; clusters = connected components over edges with w ≥ 3. A cluster spanning ≥ 3 folders is a
  SCATTER. A cluster of > 30 files is reported (`… too big for one pass`) with no MOVE rows.
- Cluster name: the most frequent lowercase token of its files' basenames (split on non-alphanumerics
  and camelCase), ≥ 4 letters, not one of `index main test tests spec util utils helper helpers common
  shared component components hook hooks service services type types model models view views page
  pages style styles lib src core base impl mock mocks data config constants`; ties alphabetical; none
  → the stem of its most-connected file.
- Home: `<deepest common parent of the cluster's files>/<name>/`; when that parent is the root and
  `src/` holds any of them, `src/<name>/`. An existing folder of that name is used as is.
- MOVE rows: every cluster file not already in its home → `<home><basename>`; a basename collision or an
  existing target drops that file. GUARDRAIL: a cluster whose home would pass 30 files gets no MOVE
  rows (one giant folder must never win the score). Order: clusters by (folders spanned − 1) × commits
  touching the cluster, descending, then name; files alphabetical inside a cluster.
- MAP: folders with ≥ 1 movable file directly inside — files, purpose (guide → `README.md` heading →
  `-`), guide yes|no; largest first, then name. GUIDES: folders with ≥ 5 movable files directly inside
  and no guide. STALE: § 0.1 citations.
- The screen (bare `hops`), ≤ 40 lines, this order, an empty section prints nothing:
```
hops — <F> folders per change over <N> changes · guides <g>/<G> folders of 5+ files
MAP       <dir>/ · <n> files · <purpose> · guide <yes|no>          (≤ 12, then: MAP       +<k> more folders)
SCATTER   <name>: <k> folders → <home> (<m> files)                  (≤ 8)
MERGE     <from> + <into> (<la>+<lb> lines, together <c>×)          (≤ 4 — T-251)
SPLIT     <file> (<lines> lines, pulls in <k> folders) · <dir>/ (<n> files)   (≤ 4 — T-251)
GUIDES    missing: <dir>/ (<n>) · <dir>/ (<n>) …                     (one line, ≤ 8 folders, then +<k>)
STALE     <guide> cites <path> (missing)                            (≤ 4, then: STALE     +<k> more)
next: bash ops/polaris hops --tsv lists every row · ops/roles/TIDY.md runs the pass
```
  Under 20 tracked files the whole output is `hops — <n> tracked files: too small to measure`, rc 0.
- `--tsv`: no caps, no header, TAB-separated, in this order: `SCORE <F> <N> <g> <G>` ·
  `MAP <dir>/ <n> <purpose|-> <yes|no>` · `SCATTER <name> <k> <home> <file,file,…>` ·
  `MOVE <from> <to> <name>` · `MERGE <from> <into> <c>` (T-251) · `SPLIT <path> <lines|files> <k|->`
  (T-251) · `GUIDES <dir>/ <n>` · `STALE <guide> <path>`.
- `--stale`: only the STALE rows; rc 0 when any, rc 1 when none. Cheap: guides only — no history, no
  index build (drift and the verify warning call it).

### 1.6 Moves — `--score`, `--owned`, `--proof`, `--remap` (T-248)
- `--score <moves>`: line 1 `score: <F> → <F′> folders per change (<pct>% fewer) · guides <g>/<G>`; then
  one line per cluster the moves touch: `change <name>: <k> folders → <k2>`. F′ = the same history with
  every `from` renamed to its `to` (a merge's `from` to its `into`).
- `--owned <moves>`: one path per line, `LC_ALL=C` sorted, unique — every `from`, `to` and `into`; the
  tracked `.meta` of each Unity asset and its future name; every file with a resolved import edge to a
  `from` (aliases included); every non-code file mentioning a `from`'s tail (§ 1.1). That list + the
  guides + `CLAUDE.md` + `ops/LAYOUT.tsv` is a tidy task's `files_owned`.
- `--proof <moves>` — the guarantee (G5, G6). Runs in the repository of the CURRENT directory (the tidy
  task's worktree) against `git merge-base <base> HEAD`, over the working tree (staged + unstaged, so a
  step is proven BEFORE its commit). Green iff: every deleted path is a `from`, every added path a `to`;
  every `to` exists and its `from` does not; every changed line pair in every changed file is (a)
  identical once each `from`→`to` substitution is applied to the old line — as a path, as its tail and
  as a dotted python module (`a/b/c.py` ↔ `a.b.c`) — or (b) an import whose resolved target is the moved
  counterpart of the old line's target; a merge's `into` gains only lines of its `from` (after
  substitution) and import edits. Edits confined to guide blocks, the root-map block and
  `ops/LAYOUT.tsv` are exempt. Green: `proof: ok — <n> moved, <m> merged, <l> lines changed, every one a
  path` rc 0. Red: one line per offence `proof: RED <path>:<line> — <reason>` (`logic changed` ·
  `not in the moves` · `<to> missing` · `<from> still exists`), rc 1. A Java/Go `package` line change is
  red — it is not a path — which is correct; rule 9 keeps those files out of proposals anyway.
- `--remap <moves>` (G8): rewrites `<root>/.polaris/harness-baseline.json` in place — in `modules`, a
  python entry (dotted, from a `.py` path) or a node entry (a path) whose source is a `from` becomes its
  `to`; a merge's `from` entry is dropped; `routes`, `scripts` and order untouched. rc 0
  `remap: <n> module names moved in .polaris/harness-baseline.json`; no baseline → rc 1
  `remap: no .polaris/harness-baseline.json — nothing to remap`. Never a blind refresh: a module that
  genuinely vanished still fails the harness.
- FIXED rule 9 (§ 1.4) lands here, with its own golden cases.

- MERGE: movable pairs, both ≤ 40 lines, touched together in ≥ 3 commits AND in ≥ 75 % of the commits
  touching either → `MERGE <smaller> <larger> <c>` (the smaller folds into the larger; ties
  alphabetical). Never a MOVE row: a merge needs the human's up-front yes.
- SPLIT: a file ≥ 600 lines whose commits also touch ≥ 4 other folders (each in ≥ 2 commits) that are
  neither its own folder nor an ancestor → `SPLIT <file> <lines> <k>`; a folder with > 40 movable files
  directly inside → `SPLIT <dir>/ <n> -`. Reported only; a pass never acts on it.
- `--due` (G17, N3), in order, each step final:
  1. `hops: off` → not due.  2. < 20 tracked files → not due.
  3. a self-hosting kit repo (`kit/ops/pack.py` tracked — the same test `update --auto` uses to skip
     itself) → not due: the pass never offers itself on POLARIS's own source (bare `hops` still reports).
  4. cooldown: the last pass (§ 0.4) exists and `git rev-list --count --no-merges <sha>..<base>` < 30
     → not due.
  5. compute: saving = (F − F′) / F with F′ applying the FIRST 25 MOVE rows (one pass's cap) — keep rows
     and FIXED are already out; unguided = the GUIDES rows. Due iff saving ≥ 0.15 or unguided ≥ 3.
  Due → ONE line `layout pass due — <reasons joined by " · ">` (`~<pct>% fewer folders per change` ·
  `<n> folders of 5+ files have no guide`), rc 0. Not due → silent, rc 1. Every run rewrites § 0.5.
- `--facts <dir>` (G16): ≤ 15 lines; a guide is written from these, never by exploring:
```
facts <dir>/ — <n> files · purpose: <guide | README heading | ->
entry files: <file> (<k> importers) · …                    (≤ 3, by fan-in)
key symbols: <name> · …                                    (≤ 8, find's ranking)
changes with: <dir>/ (<c>×) · …                            (≤ 4)
tests: <path> · …                                          (≤ 4 — test files importing a file here)
- <file> — <lines> lines · <top 3 symbols>                 (≤ 10 such lines)
```
- `--questions`: ≤ 3 lines `Q<n>: <question> — <a> | <b> (default: <a>)`, MERGE rows first, then
  framework-looking folders (§ 1.4 rule 2): `Q1: merge <from> into <into>? — no | yes (default: no)` ·
  `Q2: is <dir>/ routed by a framework (keep it where it is)? — keep | allow moves (default: keep)`.
  Nothing to ask → silent, rc 1; else rc 0.
