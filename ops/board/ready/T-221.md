## Why
An agent elsewhere found tasks marked done whose code never reached main after about four lanes landed within two minutes. Before anyone fixes the landing path we need to SEE it fail. Write a hermetic golden (read ops/contracts/safe-landing.md section 8 first, it is the spec): a throwaway repo under mktemp -d, the CLI run from inside it (copy qa-stamp.cmd's fixture style), 4-6 tasks already in review/ with DISJOINT files_owned and their own feat/<ID> tips, risk: normal set explicitly, test_select UNSET, and an ancestor suite stamp present like qa-stamp.cmd makes (this keeps last sprint's dirty-tree + ancestor-stamp + test_select-unset lesson in the landing golden). Start every lane's tail at once in the background (today's separate land, seal, done processes, the way self_land runs them), wait for all of them, then print only facts: OK <ID> or LOST <ID> per done task (byte-compare main's file with the feat tip's), waves: <n>, leftover-unsealed: <n>. The .expected file holds the GREEN output (every task OK, waves: 1, leftover-unsealed: 0, no shas, paths or times). Budget the whole golden at about 15 seconds or less.

## Acceptance criteria (binary)
- [ ] the golden is hermetic (mktemp -d, trap cleanup, no live-board writes)
- [ ] run against today's code it is RED and the red output names the lost task; run it several times (this is Windows, where the loss happened) and record in Notes how many runs went red
- [ ] if it can NOT be made red: do not fake it. Notes lists every interleaving tried (lane counts, start offsets, which step was delayed) and the golden ships as a green regression guard
- [ ] .expected is the green output and contains no sha, path, time or user
- [ ] the verify: lines pass (they check shape only; red-on-today is proven by your one manual run)
